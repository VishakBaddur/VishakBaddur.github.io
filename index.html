The data came from space. The samples came from the ground.

I built the pipeline end to end. Savitzky-Golay filtering to clean the spectra, PCA to tame 177 bands, Random Forest and Gradient Boosting, cross-validation, hyperparameter tuning. Then I checked it the only honest way, against the ground.

R2 of 0.79 for zinc. Spatial estimation maps validated against all 104 ground-truth samples. Feature importance evaluated per band. Presented directly to ISRO stakeholders.

DistributedDB

Key-Value Store with Raft Consensus / C++17

I wanted to understand distributed consensus well enough to defend every design decision. Reading the paper wasn't enough, so I wrote Raft from scratch in C++17: leader election, log replication, majority commit, and a persisted term, vote and log, behind an async TCP server on Boost.Asio with a write-ahead log (group-commit fsync). Three nodes, one docker compose up, persistent volumes, auto-restart.

Then I made it earn its numbers. A lock-ordering deadlock appeared only under 50 concurrent clients. I profiled the write path, found the commit bottleneck, and took cluster throughput from 130 to 5,100 writes/sec.

3-node cluster: 5,000+ majority-committed writes/sec across 50 concurrent clients, 100% success over 50,000 operations, fsync on every commit. Leader re-elected in 181 to 293ms across 12 leader-kill runs. Recovers with data intact after all three nodes are killed at once. Single node: 39,000+ put/get pairs/sec, crash recovery verified with kill -9.

Flowforge

Distributed Workflow Engine / Java 21, Spring Boot, Kafka, PostgreSQL, Redis, Kubernetes

The follow-up question was the one I like most: what happens when something dies at the worst possible moment? Flowforge is an event-driven workflow engine with DAG scheduling, event sourcing, retries, leases, idempotency and dead-lettering. It sustained 10K+ tasks/sec across about 4,400 concurrent workflows, with 0 lost or duplicated tasks in a 510K-task test. Profiling and fixing bottlenecks took the same workload from 889 to 5,615 tasks/sec (6.3x) with parallel consumers, batched Postgres writes and pipelined Redis.

Then I tried to break it. kill -9 on workers at bad moments. It worked, and it found a bug: a Redis claim lasting 7 seconds outlived Kafka's 6-second redelivery, so a redelivered task saw a dead worker's claim, skipped it, and nothing ever retried it. 4 of 200 workflows hung. The fix was a two-phase claim: a 3-second first claim, extended with an atomic Lua check-and-set only once the task start is durable, plus a startup check that refuses to boot if the claim TTL is not below Kafka's session timeout. Three repeat kill tests: zero stuck.

I also ran a real workload on it, an incremental NYC 311 ETL. A worker crashed mid-run and the checksums still came out identical, and a data-quality gate blocked a schema break.

State recovered in 10 to 63ms after a kill (rebuild time, not failure detection). 555ms graceful failover. 0 lost workflows across rolling restarts. 323K rows in 28.6s across 30 partitions into a PostgreSQL star schema.

Honest footnote: all of this ran on one laptop with near-empty tasks, and Kubernetes was a local single-node cluster. It measures the engine, not the work. I would rather say so before you ask.

// open_source

The bugs I couldn't leave alone.

Then I started reading other people's code the way I read a stack trace: all the way down. marimo is a reactive Python notebook used by thousands of AI/ML researchers (22k+ stars). I found bugs. I fixed them. Eight times, since March 2026.

The one that took longest: a disabled cell kept showing its ancestor's error after recovery. The cause lived in three layers: the wrong backend code path, stale snapshot timing, and a frontend state machine that never cleared the errored flag. 24 commits, 4 maintainers.

The one I like best is an argument. A maintainer suggested a fix for Ruff's blank-line rules. I showed a counterexample where it corrupted output, and my approach was the one that merged. The quiet one: one cached realpath call in a hot path took autoreload from 12ms to 0.17ms per cell (62x).

// google_summer_of_code_2026

The proposal said AI. The code said otherwise.

Google Summer of Code 2026, C2SI organization, project B0Bot: an agentic AI cybersecurity news system. The proposal described a conversational AI. When I opened the code, it was fully rule-based, with zero real LLM calls behind it.

So I built what the proposal had only claimed: a 5-agent LangGraph pipeline (Planner, Scraper, Analyzer, Responder, Notifier), each enforcing input/output contracts through a shared state schema, independently unit tested across 28 tests with full mock coverage. Real LLM intent classification and grounded article responses. And I switched on the hybrid keyword/vector search that was sitting dormant in the codebase.

Sentiment was a constraint problem: no labeled cybersecurity sentiment dataset exists anywhere. I weighed keyword rules, VADER, fine-tuning and DistilBERT against that, and shipped per-article DistilBERT SST-2 inference at 11ms on CPU.

Then the bug the tests couldn't see. Subscribe requests appeared to succeed but never wrote to the database, unnoticed for three weeks because mocked tests can't catch a missing write. I rebuilt it as a single verified insert path. Silent failure eliminated, twice over: once in the parsing layer, once in a bug the test suite itself was blind to.
